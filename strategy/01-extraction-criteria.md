# 抽取判準與分期 —— 決定「做哪一支 MCP」的唯一程序

**性質：** 產物（canonical）｜**原稿：** `strategy/source/`
**這份檔案回答一個問題：在什麼條件成立之前，本 repo 不寫任何 MCP server。**

---

## §1 為什麼需要一道判準

因為這條線最可能的死法不是「做不出來」，是**做出一堆沒人呼叫的 MCP，
然後在 registry 上看起來很成功**。

```
一支沒人呼叫的 MCP，在 registry 上與一支有人呼叫的長得一模一樣。
```

install 數會漲、registry 收錄數會漲、star 會漲，而 token 消耗是 0。
**這五個數字全部可以在零 token 消耗的情況下變好看**，所以它們不能當判準。

---

## §2 抽取判準（三條 AND，全過才是候選）

```
候選 = 在真實 workflow 執行紀錄中被呼叫 ≥ 20 次／週
      且 ≥ 2 個不同 Stage 都會用到
      且 不需要新蓋能力（已在手）
```

| 條件 | 擋掉什麼 | 為什麼是這個門檻 |
|---|---|---|
| **≥ 20 次／週** | 偶爾用一次的能力 | 低於這個數，包成 MCP 的維護成本大於省下的重複工。⚠️ **20 這個數字目前沒有外部依據，是我方設的起點**（OMSN-G6） |
| **≥ 2 個不同 Stage** | 只服務單一步驟的能力 | 只有一個地方會用，寫成 skill 或腳本就夠了。**MCP 的價值在跨 workflow 複用** |
| **不需要新蓋能力** | 「順便做一個新功能」 | 抽取是重新包裝既有能力。要新蓋能力，那是另一個立案，走另一條判定 |

**三條都是 AND。任一條不過，不是「先做起來放」，是不做。**

## §3 六個候選的現況（全部未驗證）

上游列的六個名字是**提案時想出來的**，沒有一個做過需求驗證（OMSN-G5）。

| 候選 | 能力是否在手 | ≥2 Stage？ | 呼叫紀錄 | 判定 |
|---|---|---|---|---|
| `video-transcript-mcp` | 是（Media House L1） | 未知 | 無 | ⬜ 待驗 |
| `creator-research-mcp` | 部分（L0.5 目錄採集，依賴第三方平台） | 未知 | 無 | ⬜ 待驗 |
| `social-content-mcp` | 否 | 未知 | 無 | ⬜ 待驗 |
| `model-price-mcp` | **是**（平台快照 109 模型定價） | 未知 | 無 | ⚠️ 邊際成本低，但仍缺需求證據 |
| `token-usage-mcp` | **是**（`list_usage` 明細） | 未知 | 無 | ⚠️ 同上 |
| `prompt-cost-mcp` | 部分（需成本引擎） | 未知 | 無 | ⬜ 待驗 |

**⚠️ 「邊際成本低」不是「有人要」。**
`model-price-mcp` 與 `token-usage-mcp` 誘人的地方正是它的陷阱：因為好做，
所以會先做；因為先做了，所以會被當成這條線已經啟動。**做起來很容易的東西，
最容易被拿來代替判準。**

## §5 探針（前置未滿足時，唯一被允許的動作）

```
探針（Phase 3 跑滿之後，1 週）：
  只做「呼叫次數盤點」—— 不寫任何 MCP。
  從 4 週執行紀錄算出 §2 那三條的結果。
判準：能不能指出一支同時過三條的能力。
     指不出來 → 本條延後，不是硬做。
成本：0
```

**探針的合格輸出包含「指不出來」。**
一份盤點如果每次都剛好指出一支值得做的 MCP，該被懷疑的是盤點方法，不是運氣。

### ⚠️ 一個被明確排除的捷徑

「先隨便做一支，發布出去看有沒有人用」——**不採用**。
理由不是保守，是它量不到想量的東西：registry 上的安裝來自瀏覽的人，
不是來自 workflow 的重複呼叫。**用安裝數去回答呼叫問題，答案會是錯的而且看起來像對的。**

若要走一次發布流程以解 OMSN-G1（發布、版本化、registry 登錄全部沒走過），
那應該被明確定性為**流程探針**，且事先寫下「這一支的 `call/wk` 預期是 0」——
**寫在事前，才不會在事後被讀成成功**（見 `strategy/00-overview.md` OMSN-D2）。
